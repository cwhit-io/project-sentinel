# Architecture

This describes the intended commissioning baseline, not an accepted production deployment. The disposable PostgreSQL/Zabbix core was started and internally checked; no runtime component was end-to-end accepted. For what Sentinel does and does not own, see [`docs/scope.md`](scope.md).

Git is the intended desired-state layer. YAML inventory and policy files feed the controlled operator, which currently validates local references and produces a deterministic review-required plan. The live discover/apply/verify/export lifecycle and narrow Zabbix API adapter are not operationally accepted; apply is hard-disabled, rejects before parsing or mutation, and writes no receipt. Zabbix Server and Web are configured to use PostgreSQL. The intended event path is Zabbix to StackStorm through an authenticated webhook, but Compose intentionally has no runnable StackStorm deployment or automation profile. The disabled contracts are desired-state intent only, and receipt/remediation remain blocked.

Plan `integrity` is an unkeyed integrity checksum for accidental or untrusted-file tampering detection. It is not authentication, provenance, authenticity, review, or approval; verified plans are independently rebuilt from validated desired state.

The inventory schema now also accepts `collection_method: http` for HTTP uptime assets, with a closed `http_checks` array describing the probe (`name`, `target_url`, `method` GET-only, `interval_seconds` 60..3600, `timeout_seconds` 1..30, `expected_status_codes`, `follow_redirects`, `verify_tls`, optional `body_match`). The desired-state contract uses `target_url` instead of `url` so the artifact store's closed locator-key denylist is not tripped when the plan is serialized for review. The synthetic HTTP uptime asset `bhm-org-uptime` lives alongside the lab agent and is validated by `sentinel validate`; the agent and HTTP uptime are scope-isolated via `tags.scope=lab` and `tags.scope=public-uptime` respectively.

The Zabbix API surface is split into two closed policy documents. `automation/zabbix/api-policy.yaml` keeps the read-only methods (`apiinfo.version`, `host.get`, `hostgroup.get`, `template.get`, plus the bounded `httptest.get` and `item.get` for the HTTP snapshot). `automation/zabbix/probe-policy.yaml` declares the bounded write methods (`host.create`, `host.update`, `httptest.create`, `httptest.update`, `item.create`, `item.update`) and marks `host.delete`, `httptest.delete`, and `item.delete` as `executor: none`. The runtime read client and the runtime write client are exact distinct types backed by exact distinct transport and handle classes; they cannot cross.

The reconcile path is the only Sentinel mechanism that can ever call a write client. `sentinel reconcile --apply-if-signed` is gated by an Ed25519 SSH signature over the plan file. The signature is produced by `ssh-keygen -Y sign` and verified by `ssh-keygen -Y verify` through `automation/reconciliation/approval.py`. `automation/reconciliation/approver.py` provides `manual_sign` and `auto_sign_or_stop`; the auto-sign marker is `~/sentinel-state/auto-sign-enabled`. Approval verification raises `PermissionError` on any payload, signature, key, identity, or namespace mismatch without reflecting contents. `sentinel apply` remains hard-disabled before parsing, signing, or any I/O.

Compose retains separate internal service networks. PostgreSQL and the synthetic agent remain off the operator-facing network bridges. There is no StackStorm operator network. Ordinary Docker bridge NAT and broader host-routed, Docker-gateway, LAN, and Internet paths remain unverified. The user accepted ordinary Docker bridge NAT risk only for synthetic sandbox commissioning. Per `docs/scope.md`, TLS termination and reverse proxy are operator-managed outside Sentinel, and Zabbix and StackStorm are trusted upstream platforms; Sentinel does not configure TLS, certificates, reverse proxies, or hardening for either platform.

The protected-live reconciliation boundary is a static/disposable, read-only discovery scaffold. The lowest no-proxy/no-redirect/no-cookie/no-retry transport accepts only the exact read handle and six discovery methods, rejecting all others before credential resolution. The exact read client cannot be replaced with a duck transport. Its internally derived target binding covers the canonical immutable endpoint contract, trust ID, read-handle ID, exact Zabbix `7.0.14`, and a fixed no-write marker. Closed deterministic validation runs before persistence and after bounded bundle loading. The artifact root is checked against the worktree derived from the module path, not caller input. The three bundle documents are preflighted in memory, including closed Sentinel-only tag validation, before any run directory or file is created. Approval verification is unconditional pre-input denial for legacy callers and runs the SSH verifier for the new closed payload contract. The write side is an exact distinct type with no live transport wired by default. Runtime endpoint trust and filesystem durability remain pending.

`automation/zabbix/credentials.py` now includes a `FileCredentialProvider` template that enforces owner-`uid` and mode-`0600`. It is never wired by default. No real credential file is read by Sentinel in this milestone.
