# Architecture

This describes the intended commissioning baseline, not an accepted production deployment. A disposable PostgreSQL/Zabbix core was started and internally checked; no runtime component was end-to-end accepted.

Git is the intended desired-state and recovery layer. YAML inventory and policy files feed the controlled operator, which currently validates local references and produces a deterministic review-required plan. The live discover/apply/verify/export lifecycle and narrow Zabbix API adapter are not operationally accepted; apply is hard-disabled, rejects before parsing or mutation, and writes no receipt. Zabbix Server and Web are configured to use PostgreSQL. The intended event path is Zabbix to StackStorm through an authenticated webhook, but Compose intentionally has no runnable StackStorm deployment or automation profile. The disabled contracts are desired-state intent only, and receipt/remediation remain blocked. OpenBao is intended to hold sensitive values, accessed by opaque references. Only a sealed/uninitialized internal TLS/API startup succeeded; bootstrap and secret use were not performed.

Plan `integrity` is an unkeyed integrity checksum for accidental or untrusted-file
tampering detection. It is not authentication, provenance, authenticity, review,
or approval; verified plans are independently rebuilt from validated desired state.

Compose retains separate internal service networks. Loopback-published services use namespace-scoped, non-internal operator bridges split by service group: `openbao-operator` contains only OpenBao and `zabbix-operator` contains only Zabbix server and web. PostgreSQL and the synthetic agent remain off every operator bridge. There is no StackStorm operator network. Thus there is no shared operator Docker bridge; this does not prove bounded egress or absence of lateral reachability. Host-routed, Docker-gateway, LAN, and Internet paths remain unverified. The user accepted ordinary Docker bridge NAT risk only for synthetic sandbox commissioning. Production requires an explicit firewall and egress design, and a trusted-network or TLS reverse proxy remains required for shared access. OpenBao declares persistent storage and TLS configuration. Initialization, unseal, audit setup, and recovery remain protected procedures and were not performed.
