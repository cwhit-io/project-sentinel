# Recovery

This is a protected commissioning runbook, not evidence of an accepted production recovery capability. The repository is non-operational and no real credentials or recovery material may be used with it.

The intended procedure is to use `scripts/backup.sh` for an encrypted PostgreSQL logical dump plus the current sanitized **dry-run planning metadata**. The metadata archive contains only `monitoring/exports/plan.json`; it is not a Zabbix configuration export or backup and cannot restore Zabbix configuration. A sanitized live Zabbix export requires a separately implemented and verified path and is currently blocked. Apply is hard-disabled, so no `apply-receipt.json` is required or archived. “Access-controlled” here means the script enforces its fixed physical `backups/` destination, current-user/root ownership, no group/world write permission, no destination symlink, and a fail-closed atomic run lock; it is not assumed from operator intent. Extended/default ACLs, MAC policy, mount options, and remote-filesystem permissions are not inspected or enforced. Before attempting PostgreSQL backup, the script validates conservative database/user identifiers and fails closed unless current desired-state validation succeeds and the plan checksum and current-state equivalence verify through the inert review-only rollback path. PostgreSQL/encryption is one 300-second `pg_dump | age` process-group pipeline; metadata is one 60-second `tar | age` pipeline; manifest `age` is synchronously bounded at 60 seconds. Each runs under `setsid timeout --signal=TERM --kill-after=5s` and `bash -o pipefail`. Handled cleanup verifies the recorded Linux `/proc` starttime and PGID before TERM/KILL of the group, waits/reaps, then removes staging and lock state. This is not forced-cleanup assurance: SIGKILL, kernel failure, or power loss can leave state requiring adjudication. It requires an exact, nonempty encrypted member set and marker, Python `hashlib` checksums, fsyncs members and staging-directory metadata before required Linux `renameat2(RENAME_NOREPLACE)`, and fsyncs the parent afterward. It fails closed if no-replace rename is unavailable. The script never prunes and rejects retention/prune overrides; every published set is preserved. Retirement is a separate protected operator procedure only after protected decryption and successful isolated restore verification. Encrypted backup and OpenBao volume procedures were not executed.

The lock metadata contains PID, `/proc/<pid>/stat` starttime, UTC, and set/run ID. Contention always fails closed;
the script never auto-deletes a contended lock. A protected operator may remove
only `backups/.backup.lock` after completing the exact identity, process-group,
host command-chain (`setsid`, `timeout`, `bash`, `docker compose exec`, `pg_dump`,
`tar`, `age`), container-side `pg_dump`, and staging checks in `docs/backup.md`.
Missing or partial metadata and unexpected ownership require escalation rather
than deletion. SIGKILL, kernel failure, or power loss may leave lock/staging state.

It does not test an encrypted artifact, age identity/custody, manifest or offsite handling, roles/global objects, PITR, or production recovery. Back up OpenBao data and audit volumes separately with an approved encryption recipient, keep recovery material outside the backup location, and never store unseal keys beside snapshots. Test restores with synthetic, non-production secrets only. Production recovery is not accepted until the isolated application stack is safely validated and component-specific TLS, audit, identity-revocation, integrity, and recovery objectives are verified.

All disposable source, restore, and application containers, project networks, named volumes, and explicitly inventoried anonymous volumes were removed after the run. Unrelated volumes/images and commissioning TLS were preserved. No real credentials or recovery material were used.

Choose and document one PostgreSQL backup method; do not mix their claims or restoration requirements:

- **Logical backup while PostgreSQL is running:** use the approved `pg_dump` workflow to create a consistent database dump, encrypt it to the approved recipient, and retain its checksum and custody record. Restore with compatible PostgreSQL tooling into an initialized, isolated destination and use `pg_restore`; roles and other globals require a separately protected `pg_dumpall --globals-only` artifact and remain blocked in current evidence.
- **Physical named-volume archive:** first perform a clean PostgreSQL shutdown and verify the PostgreSQL process has exited before archiving its data volume. Merely stopping application writes is insufficient. Encrypt the archive, record checksum and custody, and restore it only with a PostgreSQL version, architecture, extensions, and data-directory layout compatible with the physical cluster, into an isolated destination while PostgreSQL is stopped.

For either method, verify the encrypted artifact without decrypting it into a shared location and perform a fresh isolated restore test. Never put recovery shares, tokens, private keys, password values, or decrypted archives in this repository. Fsync and same-filesystem rename cannot guarantee persistence across every filesystem, network/overlay layer, controller cache, device, hardware fault, or power-loss mode. Nonempty ciphertext and hashes do not prove decryptability or plaintext integrity; only protected decryption and isolated restore verification can support those claims. Neither method, encrypted-artifact handling, globals restoration, nor repeatability has been accepted here.

For a future rollback, preserve planning metadata and audit records. There is no apply or reverse-operation path in this baseline, and the archived dry-run plan is not configuration recovery material. A future separately implemented, sanitized Zabbix configuration export would need its own verified backup and restore procedure. No live apply, export, or rollback has been accepted. Component upgrades require a tested backup, pinned image change, health verification, and a documented rollback to the prior image and data backup.
